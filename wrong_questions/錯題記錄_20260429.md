### Q2-1
**情境**：某企業使用生成式 AI 進行文字分類，初期僅根據既有業務資料設計少量樣本提示（Few-shot Prompting）。當模型應用至新市場資料時，團隊發現分類結果明顯不穩定，且原先提供的範例並未涵蓋新市場常見的表達方式。

- **你的答案**：3. Prompt 設計無法引導模型擷取共通特徵
- **正確答案**：2. 少量範例難以涵蓋新情境的資料差異

**解析**：
Few-shot Prompting 的核心限制在於「範例數量有限」。當企業只在既有業務資料上設計少量範例時，這些範例只能代表特定市場的語言模式和表達方式。一旦模型應用到新市場（新語境、新表達方式），原先的 Few-shot 範例完全沒有覆蓋過這些新情境，模型當然無法正確分類。
選項 1 說「過度記憶訓練資料」，這比較像過擬合問題，不是 Few-shot 本身的核心瓶頸。選項 3 說「Prompt 設計問題」，如果 Prompt 有問題，在原本的市場也會失敗，不會只有新市場才失敗。選項 4 說「模型推理能力不足」，如果模型本來就不會推理，一開始就會失敗，不會只在新市場失敗。
因此根本原因就是「少量範例不足以涵蓋新情境的資料差異」，這正是 Few-shot 在領域偏移（Domain Shift）時失敗的經典原因。

**破題攻略**：
看到「Few-shot + 新領域 / 新市場 / 新語境 → 效果變差」→ 先想「Few-shot 的範例太少，無法覆蓋新情境的多樣性」。Few-shot 適合「訓練資料和測試資料分布相似」的場景，不適合分布差異大的跨領域遷移。

### Q2-2
**情境**：某企業導入 No-Code/Low-Code 平台開放各部門自行開發應用。半年後出現：功能重複的系統多個、資料欄位定義不一致、部分應用未經審核即上線、權限與維運管理混亂。

- **你的答案**：4. 系統整合與自動化能力尚未完善
- **正確答案**：1. 缺乏統一的開發與上線管理機制

**解析**：
這一題的核心在於「根本原因 vs 表象」的分辨。
功能重複（多個部門做類似的系統）→ 因為沒有統一的應用開發管理，部門各做各的。
資料欄位不一致 → 因為沒有統一的資料治理標準，各部門自行定義。
應用未經審核就上線 → 因為沒有統一的審核流程和上線規範。
權限管理混亂 → 因為沒有統一的帳號和權限管理政策。
所有問題的根源都是「缺乏統一的開發與上線管理機制」——沒有這個機制，各部門自由發揮，自然產生混乱。
選項 4 說「系統整合能力不足」，這只解釋了部分問題（功能重複可能是整合不好），但無法解釋「未經審核就上線」和「權限混亂」。選項 2 說「平台自主性過高是根本原因」，這是倒因為果——自主性是優點，管理機制才是問題，不能因為出了問題就把自主性說成缺點。

**破題攻略**：
No-Code/Low-Code 平台的核心風險不是「技術不行」，而是「治理跟不上」。功能重複 + 資料不一致 + 審核缺失 + 權限混亂 = 缺乏統一管理機制，這四個症狀幾乎是綁在一起的，看到類似的描述直接聯想「治理機制缺失」。

### Q2-3
**情境**：某企業導入生成式 AI 系統，希望自動產出客服回覆與內部文件摘要。系統需能理解使用者輸入的完整語句內容，並在回覆中維持語意連貫，即使對話內容較長仍能保持上下文一致性。

- **你的答案**：4. 生成對抗網路（GAN）
- **正確答案**：3. 基於 Transformer 架構的自迴歸模型（Autoregressive Model）

**解析**：
這一題是經典的「生成式模型架構選擇」題。
題目關鍵需求有兩個：① 能理解完整的長文本語意，② 能維持上下文一致性。這兩個需求湊在一起，就是 Transformer 自迴歸語言模型的定義。
Transformer 的 Self-Attention（自注意力機制）能夠處理長距離依賴關係，讓模型在生成每一個字時都能「看到」上下文的所有位置，這是它能維持長文本上下文一致性的關鍵。
GAN（生成對抗網路）的主要用途是生成圖像、影片等非序列資料，雖然也有文字生成的 GAN 研究，但並不是主流的文字生成架構，更不擅長處理長文本的上下文一致性。CNN 擅長局部特徵提取，不擅長捕捉長距離依賴。RNN 有梯度消失問題，長期記憶效果差。
所以答案就是 Transformer 自迴歸模型（GPT 系列、LLaMA 等）。

**破題攻略**：
「長文本 + 上下文一致性 + 文字生成」→ Transformer 自迴歸模型。這三個關鍵字幾乎是綁定的，看到任兩個就要聯想 Transformer。GAN = 圖像生成，CNN = 局部特徵，RNN = 序列但有長期記憶問題。

### Q2-4
**情境**：某智慧製造廠導入語音互動 AI 助理，系統流程：語音轉文字 → 語言模型生成回覆 → 即時查詢內部系統資料。測試結果：語音轉文字在專業術語上錯誤率偏高；語言模型回覆偶爾不夠精準；系統回應速度略慢但仍在可接受範圍。若專案目標為優先確保正確執行指令，最合理的改進順序是？

- **你的答案**：3. 優化系統效能 → 強化語言模型 → 優化語言模型與知識補充 → 調整生成參數
- **正確答案**：2. 強化語音模型 → 優化語言模型與知識補充 → 調整生成參數 → 優化系統效能

**解析**：
這一題是「Pipeline 瓶頸分析 + 優先順序」題。
系統流程是一個串聯 Pipeline：語音轉文字（上游）→ 語言模型（下游）→ 查詢系統（更下游）。
問題嚴重程度分析：
① 語音轉文字錯誤率高 = 最嚴重。專業設備術語辨識錯誤，後面的語言模型拿到錯誤的文本，就算語言模型再強也無法挽回。「上游錯了，後面全部受影響」。
② 語言模型回覆不夠精準 = 次要問題。需要補充領域知識和微調，但前提是上游輸入是正確的。
③ 系統速度略慢但可接受 = 最輕微。還在可接受範圍內，不是最優先要處理的。
所以合理的順序是：先修最根本的問題（語音轉文字）→ 再修下游（語言模型+知識）→ 再微調（生成參數）→ 最後優化效能（速度還在可接受範圍）。
選項 3 把「優化系統效能」放在第一位，這是倒因為果——速度慢但可接受，不是最優先的問題。

**破題攻略**：
Pipeline 瓶頸處理原則：**先修上游，再修下游**。上游的錯誤會被下游放大，上游錯了後面再好也沒用。優先順序永遠是：根本原因 > 間接影響 > 錦上添花。

### Q2-5
**情境**：企業在評估 AI 決策模型是否存在資料分布偏差時，下列何者最屬於偏見檢測（Bias Detection）而非偏見緩解（Bias Mitigation）措施？

- **你的答案**：4. 調整模型決策閾值（Decision Threshold）以降低預測差異
- **正確答案**：1. 比較不同資料分布的模型預測結果分布與錯誤率

**解析**：
這一題是「檢測 vs 緩解」的觀念區分。
Bias Detection（偏見檢測）= **測量、識別、分析**偏差的過程。目標是「找出問題」，還沒有採取行動。
Bias Mitigation（偏見緩解）= **採取行動**來減少或消除偏差。目標是「解決問題」。
選項 1「比較不同資料分布的模型預測結果分布與錯誤率」→ 這是在**測量和分析**模型在不同群體上的表現差異，是典型的檢測行為，沒有做任何改變。
選項 2「重新加權訓練樣本」→ 這是採取行動改變訓練資料，是 Mitigation。
選項 3「設定輸出過濾規則」→ 這是採取行動限制模型輸出，是 Mitigation。
選項 4「調整決策閾值」→ 這是採取行動改變預測門檻，是 Mitigation。
所以只有選項 1 是 Detection，其餘都是 Mitigation。

**破題攻略**：
Bias Detection = 分析、測量、量化偏差（還沒動手）。Bias Mitigation = 動手調整（加權、過濾、閾值、重新取樣）。記憶技巧：Detection =「用眼睛看」，Mitigation =「動手改」。

### Q2-6
**情境**：某企業建置 Agentic AI 系統處理跨部門複雜任務，團隊以解決方案圖譜（Solution Graph）作為規劃框架。Solution Graph 的主要功能為？

- **你的答案**：1. 取代語言模型推理機制，改以圖形搜尋完成決策
- **正確答案**：4. 定義代理（Agent）可參考的任務分解與決策路徑結構

**解析**：
Solution Graph（解決方案圖譜）是 Agentic AI 系統中的規劃框架。
它的核心功能是：將複雜任務**分解**成多個子任務，並用圖結構表示這些子任務之間的**依賴關係和決策路徑**。Agent 在執行任務時，可以參考 Solution Graph 來選擇「下一步該做什麼」和「有哪些可能的執行策略」。
Solution Graph **不是**用來取代語言模型的推理能力，Agent 依然靠 LLM 來理解情境和做判斷，Solution Graph 只是提供一個「參考地圖」。也不是用來儲存知識案例的資料庫，也不是用來限制代理行為的工具。
選項 1 說「取代語言模型推理」，這是錯誤的——Solution Graph 和 LLM 是互補的，不是取代關係。

**破題攻略**：
Solution Graph = Agent 的「作戰地圖」，功能是「任務分解 + 決策路徑」的規劃參考。不是取代 LLM，不是知識庫，是圖結構的規劃框架。

### Q2-7
**情境**：某零售企業導入生成式 AI 商品推薦系統。測試結果：購物行為、偏好設定與價格區間相同的情況下，不同客戶族群收到的推薦商品類型仍出現明顯差異，且差異方向不易以既有行銷策略解釋。模型架構與推論設定皆未調整。

- **你的答案**：3. 降低模型參數規模以簡化決策邏輯
- **正確答案**：1. 重新檢視訓練資料的樣本分佈與代表性

**解析**：
這一題是「模型偏差來源」的經典題。
題目給的關鍵條件：① 輸入條件（購物行為、偏好、價格區間）都相同，② 只有「客戶族群」不同，③ 模型架構和推論設定都沒變，④ 輸出結果出現難以解釋的差異。
這種情況是典型的**模型偏差（Model Bias）**，根源是訓練資料的樣本分佈不均——某些族群在訓練資料中樣本數量多、某些族群樣本少，導致模型學到的模式對某些族群有偏見。
解決方向：**重新檢視訓練資料**，確認各族群的樣本數量和特徵是否具有代表性。
選項 3「降低模型參數規模」完全沒有針對性——模型架構和設定都沒變，問題不在模型大小，在資料。縮小模型反而可能讓偏差更嚴重（因為模型容量變小後，擬合能力更差）。
選項 2「限制高銷量商品曝光」會加劇問題。選項 4「增加隨機性」是掩蓋問題，不是解決問題。

**破題攻略**：
「輸入條件相同，只有族群不同 → 輸出出現無法解釋的差異」→ 模型偏差，問題在訓練資料。口訣：「架構設定都不變，輸出有差異 → 資料分佈有問題」。

### Q2-8
**情境**：隨著企業加速導入 AI，No-Code/Low-Code 平台逐漸成為模型開發與產品化的常見工具。相較於傳統自行撰寫程式的建模流程，此類平台在模型訓練機制上的典型特性？

- **你的答案**：3. 著重資料處理與轉換，模型訓練仍需外部工具完成
- **正確答案**：1. 透過視覺化介面與標準化流程，協助完成模型訓練與調校

**解析**：
No-Code/Low-Code 平台（如 Google AutoML、Azure ML Studio、DataRobot、H2O.ai 等）的核心價值，就是**降低機器學習建模的技術門檻**。
這些平台提供視覺化介面（拖拖拉垃、點一點）就能完成：資料預處理 → 特徵工程 → 模型訓練 → 評估 → 調參。
所以「模型訓練仍需外部工具完成」是完全錯誤的描述——如果還要外部工具，那跟沒有 No-Code/Low-Code 平台有什麼差別？
No-Code/Low-Code 的定位就是「不需要深厚程式技術，也能完成完整的模型訓練流程」，這是它和傳統程式建模流程最大的差異。

**破題攻略**：
No-Code/Low-Code = 「不用寫程式也能訓練模型」。關鍵字：視覺化介面、標準化流程、降低技術門檻。只要看到「還需要外部工具」這類描述，幾乎都是錯的。

### Q2-9
**情境**：某企業規劃透過 Low-Code 平台建置可視化儀表板，以支援營運數據的即時監控與分析判斷。企業特別關注儀表板顯示結果的穩定性與分析可信度。

- **你的答案**：2. 是否提供自動化決策建議與預測分析模組
- **正確答案**：1. 是否具備穩定的資料串接能力與即時更新機制

**解析**：
這一題的核心在於「儀表板的根本價值是什麼」。
儀表板的核心價值是：**準確、穩定、即時地呈現資料**。如果資料來源本身不穩定、更新不及時，那麼無論儀表板的視覺化設計多漂亮、決策建議多智能，做出來的分析都是錯誤的。
題目強調「顯示結果的穩定性與分析可信度」——這兩個東西都直接取決於「資料從哪裡來、來的穩不穩定」。
所以最應優先確認的是：**資料串接的穩定性**（不會斷線、不會漏資料）和**即時更新機制**（資料是最新狀態）。
選項 2「自動化決策建議」是儀表板的附加功能，不是核心功能。如果資料本身不可信，再好的決策建議也是錯的。
選項 3、4 的介面設計和流程觸發也都不是儀表板的根本基礎。

**破題攻略**：
儀表板的核心：「資料穩定 + 即時更新」。其他功能（決策建議、介面美觀）都是建立在這個基礎之上的。看到「穩定性 + 可信度」優先想「資料來源的穩定性」。

### Q2-10
**情境**：某企業導入大型語言模型（LLM）進行客服自動化，並已透過 Fine-Tuning 學習企業標準問答範例，但在實務運作中仍出現回應策略未符合服務優先順序及語氣與品牌風格不一致的情況。技術團隊建議再導入 Reinforcement Fine-tuning（RFT）機制，其主要目的為？

- **你的答案**：4. 降低 prompt 設計複雜度並取代訓練流程
- **正確答案**：2. 透過 reward 訊號調整模型回應策略與行為偏好

**解析**：
RFT（Reinforcement Fine-tuning）的核心機制和 RLHF（人類反饋強化學習）非常相似，都是利用**獎勵訊號（Reward Signal）**來調整模型的行為。
在客服場景中，「服務優先順序」和「品牌語氣」都是「行為偏好」——這些不是靠「知識」來解決的（Fine-tuning 已經學會了知識），而是靠「策略」來調整的。
RFT 的運作方式：人類評估模型輸出的好壞（ Reward），模型根據 Reward 調整輸出策略（Policy），讓未來的輸出更符合預期的行為模式（服務順序、品牌語氣）。
選項 4「降低 Prompt 複雜度並取代訓練流程」是完全錯誤的——RFT 和 Prompt Engineering 是完全不同的東西，RFT 是訓練階段的優化，不是用來降低 Prompt 複雜度的。
選項 1「擴展知識領域」屬於預訓練的目標。選項 3「提升推理速度」跟 RFT 無關。

**破題攻略**：
RFT = 用 Reward Signal 調整「行為偏好」（語氣、風格、優先順序）。口訣：「RFT 調行為，不調知識」——知識靠 Fine-tuning，行為靠 RFT。

### Q2-11
**情境**：某醫療院所希望改善行政效率，規劃讓各科室人員可自行建立行政回報與內部申請表單，並導入 AI 功能以自動判讀與分類填寫內容（如問題類型或需求性質），同時需兼顧流程調整彈性與降低系統開發維運負擔。

- **你的答案**：2. No-Code 平台 × 規則式自動化（Rule-based Automation）
- **正確答案**：1. Low-Code 平台 × 預訓練語言模型 API

**解析**：
需求拆解：
① 各科室人員自行建立表單 → 需要「低程式技術門檻」→ Low-Code 平台
② AI 自動判讀與分類（理解文字內容、分類問題類型）→ 需要「自然語言處理能力」→ 預訓練語言模型 API（如 OpenAI API）
③ 流程調整彈性 → Low-Code 平台支援客製化
④ 降低開發維運負擔 → Low-Code + API 的组合比自建系統成本低
為什麼 No-Code + 規則式不夠？規則式自動化（Rule-based）只能處理「符合明確規則」的情況，無法理解文字的語意。醫療院所的問題類型和需求性質種類多樣，無法用固定規則窮舉。
選項 3「傳統開發 + 自建 NLP 模型」成本最高，違反「降低負擔」的需求。
選項 4「試算表軟體」完全無法自動化處理自然語言理解任務。

**破題攻略**：
「AI 自動判讀文字 + 分類」→ 幾乎一定要用到自然語言處理 = 預訓練語言模型 API。規則式自動化擅長結構化決策（if this then that），不擅長語意理解。

### Q2-12
**情境**：在進行大型語言模型（LLM）企業專屬知識的 Fine-tuning 時，若內部 GPU 運算資源與記憶體嚴重受限，下列哪一種 PEFT 技術最能在維持模型效能的前提下，顯著降低需更新的參數數量？

- **你的答案**：2. 提示詞工程（Prompt Engineering）
- **正確答案**：4. 低秩適配（Low-Rank Adaptation, LoRA）

**解析**：
這一題是「PEFT 方法」的經典題。
題目關鍵：① 要做 Fine-tuning（不是不訓練），② 資源嚴重受限（GPU/記憶體不夠），③ 要顯著降低更新的參數數量。
LoRA（低秩適配）的核心思想：在原始模型的權重矩陣（W）旁，新增兩個小的矩陣（A 和 B），訓練時只更新 A 和 B（參數量極少），原始權重矩陣 W 凍結。
結果：訓練時的參數更新量大幅減少，但模型輸出效果接近全量 Fine-tuning。
為什麼 Prompt Engineering 不是 PEFT？Prompt Engineering（提示詞工程）**不更新任何模型參數**，純粹靠輸入的 Prompt 來引導模型輸出。這不是 Fine-tuning 的替代方案，更不是 PEFT（Parameter Efficient Fine-Tuning）的一種。
知識蒸餾（Knowledge Distillation）是模型壓縮技術，目的是訓練一個小模型來模仿大模型，不是直接用於 Fine-tuning 的。

**破題攻略**：
資源受限 + 要 Fine-tuning → LoRA。Prompt Engineering = 不改參數，不是 PEFT。記憶：PEFT = 想辦法只改很少的參數來達到接近全量 Fine-tuning 的效果，LoRA 是目前最主流的方案。

### Q2-14
**情境**：某企業規劃導入生成式 AI 助理，在正式全面部署前進行概念驗證（PoC），下列何者最不適合作為此階段的主要工作？

### Q2-16
**情境**：在生成式 AI 應用設計中，情境感知代理（Context-aware Agent）的核心特性為何？

- **你的答案**：3. 具備跨模態處理能力，可同時理解文字與影像內容
- **正確答案**：4. 能利用對話歷史、任務狀態調整行為與決策

**破題攻略**：
Context-aware = 「記得情境，調整行為」。關鍵：對話歷史 + 任務狀態 + 環境資訊。不是「跨模態」（那是另一個概念），不是「即時重訓」（成本太高），更不是「從零開始」（跟 Context-aware 相反）。

### Q2-17
**情境**：某大型物流公司計畫導入 AI 系統，以改善客服與配送作業的效率。專案團隊規劃了以下四個步驟，請問正確的執行順序為何？
1. 建立符合公司服務流程的 AI 對話邏輯與應答範本，確保顧客體驗一致
2. 明確定義導入 AI 的目標並設定關鍵績效指標（KPI）
3. 蒐集與清理過往客服紀錄與配送相關資料，作為模型訓練素材
4. 評估並選擇合適的 AI 技術供應商或開源方案，確立技術方向與架構

- **你的答案**：3 → 1 → 3 → 4（錯誤順序）
- **正確答案**：2 → 3 → 4 → 1

**解析**：
這一題是「AI 專案導入基本流程」的觀念題。

**破題攻略**：
AI 專案基本順序口訣：「目標先行，資料為王，技術跟上，邏輯最後」。記憶：蓋房子要先有設計圖（目標），備好建材（資料），決定結構方案（技術），最後裝潢（對話邏輯）。

### Q2-19
**情境**：在超長上下文任務中使用自動提示工程（Automatic Prompt Engineering, APE）時，可能面臨的最大限制是什麼？

- **你的答案**：1. 迭代優化難以因應上下文的不斷變動，導致調整失效
- **正確答案**：4. 回饋機制通常僅針對局部片段，難以全面評估最終輸出品質

**解析**：
APE（自動提示工程）的核心機制是：讓模型自己生成、篩選、迭代提示。典型方法包括讓模型針對某個任務產生多個候選提示，透過回饋信號（Reward）來評估哪個提示效果最好，再反覆迭代優化。
在「超長上下文任務」中，這個機制面臨的核心瓶頸在於：
① **回饋只能看片段**：當任務的上下文非常長時，模型很難對「整個長文本的最終輸出品質」做全面評估。回饋信號往往是基於局部片段（例如某個中間步驟的輸出），而不是整體效果。

選項 1 說「上下文不斷變動」，這不是 APE 在超長上下文中的典型問題——APE 的迭代是在固定的上下文上進行優化，不是動態適應上下文變動。
選項 2、3 都不是 APE 在長上下文下的主要限制。

**破題攻略**：
APE 的核心瓶頸 = 「局部回饋 vs 全局品質」。超長文本很難對最終輸出做全面評估，所以 APE 的迭代優化效果會大打折扣。記憶：「看局部，不看整體 → 評估不全面」。

### Q2-20
**情境**：某公司開發的智慧車載語音助理，可透過語音辨識（ASR）辨識駕駛語音，再由 LLM 生成回答並查詢車載 API。測試中發現：ASR 對汽車專業術語辨識錯誤率高；LLM 的回覆常不精確；系統回覆延遲雖存在但仍可接受。若目標是「優先提升準確性與回答品質」，下列改進步驟的最合理執行順序為何？
1. 擴充並標註汽車領域語音資料，微調 ASR 模型
2. 微調 LLM 並加入檢索增強（RAG）
3. 優化系統架構，引入批次推論降低延遲
4. 動態調整生成溫度，平衡準確度與多樣性

- **你的答案**：1 → 3 → 2 → 4
- **正確答案**：1 → 2 → 4 → 3

**解析**：
這題跟 Q2-4 的概念幾乎一模一樣，是 Pipeline 串聯瓶頸的問題。
系統流程：ASR（上游）→ LLM（下游）→ API 查詢
問題嚴重程度分析：
① ASR 錯誤率高 → **最根本的瓶頸**。ASR 錯了，後面 LLM 拿到錯誤的語音轉文字，根本無法生成正確回覆。上游錯了後面全部受影響。
② LLM 回覆不精確 → **次要瓶頸**。需要靠微調 + RAG 來改善，但前提是輸入（來自 ASR）是正確的。
③ 延遲存在但可接受 → **最輕微**，最後優化。
④ 生成溫度調整 → 屬於 Fine-tuning 之後的微調手段，放在 LLM 微調之後合理。
正確順序：1（修 ASR 根本問題）→ 2（修 LLM 次要問題）→ 4（微調生成參數）→ 3（最後才優化延遲，因為還可接受）。
你的答案把延遲優化（3）放在 LLM 微調（2）之前，犯了「把輕微問題放在嚴重問題之前」的錯誤。

**破題攻略**：
Pipeline 優化順序原則：先修最根本的問題（ASR 錯誤）→ 再修下游（LLM）→ 再微調參數（溫度）→ 最後優化效能（延遲可接受的最後做）。口訣：「根本先修，微調在後，效能最後」。

### Q2-21
**情境**：某客服自動回應系統希望根據不同客戶群體調整回覆風格。在兼顧即時性與效果的前提下，下列哪一種方案最適合？

這個方法的優點：
- 即時性高：不需要額外推理，直接在同一次生成中完成
- 效果好：模型已經學會了根據標記調整風格的能力
- 簡單：不需要訓練多個模型，一個模型搞定所有風格
選項 3 的問題：GAN（生成對抗網路）主要用於圖像生成，用於文字生成時計算成本高、訓練複雜。而且「人工篩選最終答案」完全破壞了即時性——客服場景不可能等人來審核每一條回覆再發出去。
即時性 + 效果 → Control Tokens 是目前最主流的解決方案。

**破題攻略**：
「即時調整文字風格」→ Control Tokens / 風格標籤（在同一模型內動態切換）。GAN = 圖像生成為主，不適合即時文字客服。「人工篩選」= 破壞即時性。記憶：「風格標籤，一個模型，全部搞定」。

### Q2-22
**情境**：在 Agentic AI 的架構中，解決方案圖譜（Solution Graph）常被用來輔助代理的任務執行，其主要作用為何？

- **你的答案**：2. 僅用於保存代理的輸出結果，方便後續檢視與審計，而不影響實際推理流程
- **正確答案**：4. 作為代理在執行過程中的參考框架，用於組織決策步驟並支援任務推理

**解析**：
Solution Graph（解決方案圖譜）在 Agentic AI 中的角色：
它是代理執行任務時的「參考地圖」——將複雜任務分解成子任務，用圖結構表示依賴關係和決策路徑。代理在執行過程中，會根據 Solution Graph 來選擇下一步該做什麼、目前有哪些可行的策略。
Solution Graph **直接參與推理流程**，是推理過程的輔助框架，不是單純的「儲存輸出」的紀錄工具。
選項 2 的問題：「僅用於保存輸出結果，不影響實際推理流程」——這完全低估了 Solution Graph 的價值。它不是一個被動的紀錄工具，而是一個主動參與決策的框架。
Solution Graph 的功能類似的「作戰地圖」：軍隊行軍時不是只把地圖當紀錄，地圖會直接影響行軍決策。

**破題攻略**：
Solution Graph = Agent 的「作戰地圖」，主動參與推理決策。不是「儲存輸出的日誌」。記憶：「Solution Graph 不是檔案夾，是地圖」。

### Q2-23
**情境**：企業在導入生成式 AI 平台時，往往需要利用分散於不同部門或機構中的大量敏感文本資料。若希望在確保隱私的前提下，仍能讓模型持續優化並降低資料外洩風險，下列哪一種方法最適合？

- **你的答案**：1. 同態加密（Homomorphic Encryption）
- **正確答案**：4. 聯邦學習（Federated Learning）

**解析**：
題目需求：① 分散在不同部門/機構的敏感資料，② 隱私保護，③ 模型持續優化，④ 降低資料外洩風險。
同態加密（Homomorphic Encryption）：是一種加密技術，允許在加密狀態下進行計算。優點是「資料全程加密」，缺點是：① 計算成本極高，② 目前主要用於簡單的數值計算，不適合大規模神經網路訓練，③ 解決的是「運算時的加密」，不是「如何用分散資料訓練模型」的問題。
聯邦學習（Federated Learning）：核心思想是「資料不出本地」——每個機構在自己的本地資料上訓練模型，只把訓練好的模型參數（梯度）上傳到中央伺服器，中央伺服器聚合這些參數來更新全局模型。原始資料從來不需要離開本地機構。
這樣做的好處：
- 資料不出本地 → 大幅降低外洩風險
- 各地機構的資料可以用來共同訓練一個更好的模型
- 符合隱私法規（如 GDPR）的資料最小化原則
選項 4 完全符合題目的四個需求。選項 1 只解決了「運算時加密」的問題，沒有解決「如何用分散資料訓練模型」的問題。

**破題攻略**：
聯邦學習 = 「資料留在本地，模型參數去旅行」。同態加密 = 「資料加密狀態下運算」，但計算代價極高，不適合大規模神經網路訓練。記憶：「敏感資料 AI 訓練」→ 聯邦學習幾乎是標準答案。
